# Phase 5: Verification — /verification

Integrate the generated DUT, or the style-converted existing DUT selected by `/autoflow`, with the independently prepared verification branch. Run the saved tests and present evidence for Gate 5. Only the user can sign off. A style-conversion report does not establish functional correctness.

## Sources and preflight

Require approved Gate 2 configuration, Gate 3a verification contract, Gate 3b properties, and Gate 4 test plan. Confirm specification/configuration revisions and all file lists match the approved baseline. The contract and normative sources remain the oracle. RTL may be read for interface adapter connectivity, compilation, simulation, and structural or mutation analysis only.

Check the single design-root Makefile for tool-check, compile, individual-test, regression, mutation, coverage and, when any requirement uses formal, `formal` targets. Its help target must describe tools, versions, variables, inputs, and outputs. Use make -n to inspect commands. Save logs, versions, exit codes, and all test files. Do not run hidden EDA commands.

## Execution

1. Compile the DUT, adapter, SVA, and testbench together. An interface mismatch or compile failure stops simulation. Do not alter the contract, tests, assertions, or expected outcomes to accommodate RTL.
2. Run every selected applicable TC-ID through documented Make targets. Record actual pass/fail, simulator output, REQ-ID mapping, and reproducible command. A test is passed only when its checking logic and process exit status both pass. Record per property the antecedent hits and failures across the regression in `sim_summary.property_activity`. A property with zero antecedent hits is vacuous; its REQ-ID is not signed off until a test reaches it or the user approves an exclusion with evidence.
3. For REQ-IDs whose method includes formal, run the approved properties and assumptions with an available formal tool (for example SymbiYosys) through a documented `formal` Make target. Record per property in `formal_summary`: proven, failed with a counterexample trace, bounded to depth N, or not run with the reason. A counterexample is a verification failure; do not change the property or assumptions to remove it without a triage record and user approval. A missing formal tool is reported as not run, never as proven.
4. Analyze every non-passing test before any fix: one `failure_analysis` row per distinct failure signature with the symptom (first error line and time), category (`dut`, `testbench`, `specification`, `environment`, `tool` or `unclassified`), cited evidence, root cause, action and status. An AI-generated hypothesis cites log lines or assertion IDs and stays open until a human confirms it.
5. Run mutation checks where supported. Record each mutation, whether it compiled, whether the tests detected it, and the score. Do not count non-compiling mutants as detected. If unavailable, report N/A rather than pass.
6. Measure baseline code coverage when supported. If the user requests a target, invoke /code_coverage, show baseline first, ask for a numeric target, and save every added specification-based test.
7. Update schemas/rtm.json and schemas/verification_report.json with raw evidence and statuses. For each TC fill `purpose`, `req_ids`, `functions`, and for a non-passing test `failure_category`, `cause` and `evidence`; fill `coverage_summary` per REQ-ID without averaging unlike metrics. Keep missing, unrun, N/A, failed, and passed distinct. Apply the repository RTM schema's sign-off conditions; a per-requirement mutation score below 85% blocks that requirement's sign-off where mutation is applicable.
8. Write `docs/verification_report.md`: a summary table (tests by status, open failures by category, formal results, vacuous properties, mutation, code coverage, open reviews); the TC table with purpose, functions, status, cause and review columns (reviewer, `engineer` or `ai_agent` with model, verdict `agree`/`disagree`/`needs-info`, comment, author response); the failure-analysis table with the same review columns; the coverage summary per REQ-ID; and the exact Make targets. Mirror the review in the `review` field of each `tc_results` and `failure_analysis` entry. A review by an AI agent is advisory and never approves a gate.
9. Show the Gate 5 dashboard with each REQ-ID, properties, formal results, TC results, mutation evidence, optional coverage target, unresolved gaps, and exact Make targets for reproduction. Recommend approval only when required checks pass, no property of a signed-off REQ-ID is vacuous, and no review is open with `disagree` or `needs-info`. Record gate_5_approved=true only after explicit user sign-off.

If a tool is unavailable, state which checks were not run and how to rerun them. Do not infer a functional pass from compilation or code coverage.
